## 1. 共通約定

### 1.1 證明系統

| 用途 | 系統 | 理由 |

| zkPDF（C1）、zkTLS 隱藏值述詞（C2b，後續） | Noir 1.0 beta 線上的固定版本，後端 Barretenberg UltraHonk 的零知識版本，BN254 | `sha256_compression` 是黑箱函式（後端以查表實作）【確認：Noir 標準函式庫文件】；動態索引陣列（ROM／RAM）適合解壓縮與查表；通用 SRS（Aztec 公開儀式），不需每個電路做可信設定；驗證金鑰小，手機查驗可行 |

規則：

1. Noir 與 bb 版本在 `native/circuits/VERSIONS` 釘選，ACIR 與驗證金鑰的 SHA-256 寫在 Kotlin 常數；版本變更等於新電路（`name` 加版本）。
2. 必須使用 bb 的零知識版本產生與驗證證明。WP1 要以 bb 的說明與原始碼確認設定方式，並在驗收紀錄寫明版本與參數。【推論：bb 預設的 UltraHonk 不是零知識】
3. 所有位元組輸入以 `u8` 陣列傳入；需要成為公開輸入的位元組串，每 31 bytes 打包成一個欄位元素（大端序，最後一段左補零），長度另以 `u32` 公開。
4. 所有雜湊的網域分隔字串以 ASCII 寫死在電路與 Kotlin 兩邊，見各節。
5. 每個電路有固定的大小參數（第 3.7 節），超過就不能證明，Kotlin 端在產生前先檢查並給出原因。

### 1.2 SHA-256 中間狀態

PDF 簽章的 `messageDigest` 是 ByteRange 兩段串接的 SHA-256。令 M 為這個串接（含 SHA-256 填充），依 64 bytes 切成區塊 B₀…B_{n-1}，H₀ 為初始值，Hᵢ₊₁ = compress(Hᵢ, Bᵢ)。

- 公開區段的壓縮由查驗端在電路外計算；私密區段（「視窗」）的壓縮在電路內計算：電路取公開的 H_s（視窗起點的中間狀態）與私密的區塊 B_s…B_{e-1}，輸出公開的 H_e。
- 查驗端從頭計算到 H_s，比對公開輸入；拿電路輸出的 H_e 繼續計算，最後的雜湊值必須等於 CMS 的 `messageDigest`。
- 視窗必須以 64 bytes 對齊 M 的區塊，且不得包含 M 的填充區塊（最後一段 SHA-256 填充只在公開區段）。
- JCA 不提供中間狀態，Kotlin 端需要自己的 SHA-256 壓縮函式實作（`Sha256State`），以 NIST 測試向量與 JCA 比對。

洩漏說明：公開 H_s 與 H_e 等於公開「視窗內容的一個雜湊」。對低熵內容可以猜測比對。zkPDF 的視窗都含高熵資料（福州大學證明的頁面含 16 位十六進位驗證密鑰；其他版型以壓縮後的整頁內容為單位），描述檔要標示視窗內是否有至少 64 位元的不可猜測內容，沒有時同意畫面要提示「查驗方可以猜測比對未揭露的內容」。

## 3. C1：zkPDF 電路 `pdf_text_v1_1p`

### 3.1 陳述

給定公開的遮蔽套件 P、版型描述檔 T、綁定值 β，證明者知道私密位元組 W（視窗內容）與鹽值，使得：

1. 把 W 填回 P 後，ByteRange 的 SHA-256 等於 CMS 的 `messageDigest`（第 1.2 節，電路只負責視窗內的壓縮）。
2. 內容視窗的資料是 zlib 串流（若有 RC4 則先與公開金鑰流 XOR），完整解壓後得到內容串流 C。
3. C 符合 Word 類文字規則，並且 C 中的文字運算子表與證明者提供的提示完全一致。
4. 每個錨點是 C 中某個文字運算子，它的原始字串位元組與字型名稱等於公開輸出，且是同內容運算子中的第 k 個（k 與總數公開）。
5. 每個欄位 slot 的承諾等於 SHA-256(網域 ‖ slot ‖ 鹽 ‖ 長度 ‖ 補齊的原始位元組)，原始位元組是兩個錨點之間所有文字運算子的字串（含字型名稱）。
6. 每個述詞（例如日期不晚於 cutoff）對所指的欄位成立。
7. β 是公開輸入（綁定衍生憑證的持有者金鑰，不需要額外約束）。

電路外由查驗端確認（第 3.3 節）：CMS 簽章與信任、視窗是第 1 頁的內容串流或某個物件的串流資料、錨點解碼後等於描述檔的文字、欄位開啟資料解碼後等於揭露的值。

### 3.2 遮蔽套件（公開）

- 遮蔽後的檔案：原檔逐位元組相同，只有視窗的私密位元組以 0x00 取代（p4-zkp.md 第 5.1 節的 `document`）。
- 視窗清單：每個視窗的角色（`content` 或 `opaque`）、在檔案中的位移與長度（只含物件串流資料本身）、H_s、H_e、區塊數。
- 私密範圍以外、但落在視窗首尾區塊內的位元組（例如 `stream\r\n` 的一部分）是公開的，在電路公開輸入 `head`、`tail` 中，電路約束它們與區塊內容一致。所以私密位元組恰好是串流資料，GovBind 所說的「完整分割」由此成立。

### 3.4 電路內的子電路

```
for each window w (content 一個、opaque 最多一個):
    blocks = head_w ‖ private_w ‖ tail_w            // 約束 head、tail 等於公開輸入
    H_e = fold(sha256_compression, H_s, blocks)     // 只對啟用的區塊計算
content:
    z = private_content XOR keystream (未加密時 keystream 全 0)
    C = inflate(z)                                  // 3.4.1
    ops = lex_and_check(C, op_hints)                // 3.4.2、3.5
    anchors = select(ops, anchor_hints)             // 3.4.3
    for each claim slot: src = concat(ops in (a_before, a_after)) ; commit   // 3.4.4
    for each predicate: check(src_of(claim), table) // 3.4.5
```

#### 3.4.1 inflate

- 先檢查 zlib 標頭（CMF 的壓縮方法為 8、視窗不大於 32 KB、FDICT 為 0、`(CMF·256+FLG) mod 31 = 0`）。
- 支援三種區塊：未壓縮、固定 Huffman、動態 Huffman；區塊數上限 `MAX_BLOCKS`。動態區塊在電路內由碼長重建正規 Huffman 表（code length code 19 個、字面／長度 288 個、距離 32 個），以「每個碼長的第一個碼與偏移」查表解碼。
- 兩階段：
  - 階段 A（逐記號）：證明者提供記號序列提示（種類、值、在位元流中的位置、碼長）。電路以 ROM 讀出位元流的 4 bytes 視窗並取出所需位元（Huffman 碼以反向位元序比對），檢查記號依序相接、最後一個區塊設 BFINAL 並以 256 結束。記號上限 `MAX_TOKENS`。
  - 階段 B（逐輸出位元組）：依記號產生輸出。字面值直接寫入；長度距離對以 RAM 從 `out[k − dist]` 複製（允許重疊）。輸出長度上限 `MAX_PLAIN`，實際長度為公開以外的私密值。
- 解壓後計算 Adler-32 並與 zlib 尾端 4 bytes 比對，確認整個串流都被解完。
- 不支援 FDICT 與 32 KB 以上的視窗；遇到就不能證明。

#### 3.4.2 詞法掃描

對 C 逐位元組跑一個小狀態機：一般、註解、字面字串（含巢狀括號深度與跳脫）、十六進位字串、名稱、數字、運算子。只追蹤需要的資訊：

- 每個字串的起訖位置與種類（字面或十六進位）。
- 最近一個名稱記號；遇到運算子 `Tf` 時把它設為目前字型（只在 BT…ET 內有效，遇到 BT 時清空）。
- 運算子記號 `BT`、`ET`、`Tj`、`TJ`、`'`、`"`、`[`、`]`、`BI`、`ID`、`BDC`、`BMC`、`Do`。

證明者提供文字運算子表提示（最多 `MAX_OPS` 筆）：每筆為（運算子種類、字串在 C 的起訖、所屬 TJ 陣列範圍、字型名稱起訖）。掃描時以指標依序比對：每遇到一個字串，它必須正好是提示的下一個字串；每個提示都必須被走到（完整性）。

#### 3.4.3 錨點

- 錨點提示：（運算子索引、序數）。電路輸出該運算子的字型名稱與「字串原始位元組」（不含括號或角括號，不解跳脫；TJ 陣列中的多個字串依序串接，數字間距忽略）。
- 序數與總數：電路對所有運算子計算「字型名稱與原始位元組都相同」的指示值，前綴和得到序數，總和得到總數，兩者公開。描述檔通常要求總數為 1。
- 錨點原始位元組上限 `MAX_ANCHOR_SRC`。

#### 3.4.4 欄位承諾

- 欄位 slot 指定前後兩個錨點（公開的錨點索引）。欄位的「原始位元組」是兩個錨點之間（不含錨點）所有文字運算子的紀錄串接，每筆紀錄為 `u8 字型名稱長度 ‖ 字型名稱 ‖ u8 種類（0 字面、1 十六進位）‖ u16 長度 ‖ 字串原始位元組`。
- 承諾 = SHA-256("diw-zkpdf-claim-v1" ‖ u8 slot ‖ salt[16] ‖ u16 長度 ‖ 原始位元組補零到 `MAX_CLAIM_SRC`)。鹽值為私密輸入，每份證明重新產生。
- 原始位元組不解跳脫、不解碼，由查驗端在 V10 以公開字型資料解碼。這讓電路不必處理 ToUnicode。
- 未使用的 slot 承諾為 32 bytes 的 0，並以公開旗標標示。

#### 3.4.5 述詞

- 支援 `DATE_LE`、`DATE_GE`：把欄位原始位元組依紀錄的字型與種類切成編碼值（WinAnsi 1 byte、Identity-H 2 bytes；字面字串的 `\ddd` 八進位與 `\\`、`\(`、`\)` 跳脫在這裡處理），以公開對照表轉成數字（不在表中的編碼值視為分隔符），依描述檔格式（例如「4 位、1–2 位、1–2 位」）組成 YYYYMMDD，與公開的 cutoff 比較，結果必須為真。
- 對照表為公開輸入：最多 `MAX_DIGIT_FONTS` 個字型 × 10 個數字的編碼值，由查驗端依 V7 自行產生。
- 述詞輸入欄位可以不揭露（只出示述詞結果）。

### 3.5 Word 類文字規則（版型類別 `word-like`）

電路強制：

1. 沒有 `BI`（行內影像）與註解以外的不明區段；`BDC` 的屬性字典不得含字串（Word 的標籤只有 MCID）。
2. 每個字串之後，跳過空白、數字與其他字串後，第一個運算子必須是 `Tj`、`'`、`"`，或字串位於 `[ … ] TJ` 陣列內。
3. 每個顯示文字的運算子在同一個 BT 內之前有 `Tf`。
4. 閱讀順序以串流順序為準（描述檔作者以真實樣本確認版型符合）。

不符合規則的文件不能用這個電路，Kotlin 端在產生前先以相同規則檢查並給出原因。

### 3.8 保證與限制

- 保證：揭露或述詞所用的值，確實出現在某把金鑰簽章的 PDF 第 1 頁內容串流中，位於兩個指定錨點文字之間；簽章者是誰、是否可信由電路外的 CMS 檢查決定。
- 不保證：版面上的視覺位置（電路以串流順序為準）；欄位意義（由描述檔與錨點定義）；文件仍然有效（看列印日期與查驗方政策）；出示者就是文件上的人（持有人綁定靠自然人憑證證據，姓名須等於 MOICA 憑證 CN，見 p4-zkp.md 第 6 節）。
- 證明只綁定衍生憑證的持有者金鑰（β）；他人拿到證據包也無法放進自己的憑證。新鮮度由出示時的 KB-JWT 提供。
- Form XObject 內的文字不在 v1 範圍：它來自另一個串流，字型取自該 Form 自己的資源（可能與頁面同名），所以 `PdfTextExtractor.runs` 只列出頁面內容串流的文字，Form 內的文字不列入、也不能當錨點或欄位。三份樣本中，移民管理局兩份各有一個 Form（`Xf1`）帶一個文字運算子，其餘文字都在頁面串流，欄位不受影響。日後要證明 Form 內的文字，需在 V5 加上「頁面資源 → `/XObject` → Form 串流」的視窗與 V7 的 Form 字型，電路多一個內容視窗。

### 3.11 版型的欄位與錨點（參考 P3 文件解析）

版型描述檔自己定義欄位與錨點，P3 已支援的文件解析只作為參考：它已經知道各種文件有哪些標籤（姓名、學號、證件號碼、出境／入境等）與值的格式，可以拿來決定 zkPDF 要提供哪些欄位、用哪些標籤當錨點，但設計不必完全照它。

- 欄位名稱：意義相同時優先沿用 P3 的欄位名，讓同一個欄位不論來自 zkPDF、zkTLS 或一般衍生憑證都容易對應；不適合時由描述檔另取名稱。
- 錨點：描述檔列出每個欄位可接受的前後錨點標籤（公開文字）。標籤可參考 P3 解析器使用的標籤，但以電路需要為準：錨點在整頁只出現一次（總數為 1），而且與欄位值在不同的運算子。
- 正規化：描述檔定義欄位文字的正規化規則（去空白、日期格式等），依描述檔版本保留；可重用 P3 的輔助函式，但不依賴 P3 解析器的整頁輸出。
- 持有端的規劃（`ZkPdfPlanner`）：以 `PdfTextExtractor.runs`（WP2）列出運算子，依描述檔的錨點標籤找出欄位所在的運算子；也可以先用 P3 解析器找到欄位值，作為對照與除錯，但結果以描述檔規則為準。找不到唯一錨點時這個欄位不能做零知識，畫面寫明原因。
- 查驗端（V7、V10）：錨點解碼後要等於描述檔的可接受標籤之一；欄位原始位元組以公開 CMap 解碼後套用描述檔的正規化規則，結果必須等於揭露的值。
- 第一版只支援頁面上逐字出現的欄位與日期述詞。錢包計算得到的欄位（例如最後入境日期、某天是否在境內）仍以一般衍生欄位出示，畫面標示「由錢包計算，未經零知識證明」；之後的電路版本可加入逐列的述詞。

### 3.12 分段證明（2026-10-26 架構決定）

量測（`p4-benchmarks.md` Round 6，以及 Claude 在 4 vCPU 上以 bb 2.1.9 的 ZK prove）：

| 電路大小（dyadic） | prove（warm） | 峰值 RSS |
|---|---:|---:|
| 2^19（307,667 gates） | 9.4 秒 | 0.88 GB |
| 2^20（857,780） | 21.1 秒 | 1.8 GB |
| 2^21（1,522,748） | 42.3 秒 | 3.5 GB |
| 2^22（2,563,132） | 73.4 秒 | 6.8 GB |

完整容量的 inflate 估計約 666 萬 gates（2^23），加上 SHA 與詞法掃描約 900–1,020 萬（2^24）。依上表外推需要 13–27 GB 記憶體，手機與一般電腦都無法產生，所以 `pdf_text_v1_1p` 不做單一電路，改為**一串分段證明**：

- 每段是獨立的 UltraHonk ZK 證明，段與段之間以**加鹽的 Poseidon2 承諾**相連，公開輸入只有承諾，不公開內容。
- **不做遞迴合併**。驗證一段遞迴證明約需 70 萬 gates（2 段約 147 萬），比段本身還大。查驗端逐段驗證：每段 16,256 bytes、驗證約 0.1 秒，十幾段約 200–300 KB，可以接受。遞迴只保留為之後在高配置機器上做的選擇性合併。
- 段數隨**實際**資料量增加，而不是隨容量上限：樣本最大的 31,582 bytes 明文約 8 段 inflate。
- 每段大小上限：等級 A 手機 2^20（約 1.8 GB），電腦 2^21（約 3.5 GB）。段參數由量測決定，兩種等級可以用不同的段參數（不同電路），描述檔記錄用了哪一種。

#### 3.12.1 承諾

- `commit(tag, salt, fields) = Poseidon2([tag, salt, len(fields), fields...])`，使用 Noir 標準函式庫的 Poseidon2（BN254）。位元組每 31 bytes 打包成一個 Field（大端序，與第 1.1 節規則 3 相同）。
- `salt` 是一個私密 Field，同一份證據的所有段共用，每份證據重新產生（至少 248 位元的亂數）。不同證據之間的承諾無法連結。
- `tag` 區分種類：1 壓縮資料 `C_z`、2 明文段 `C_p[i]`、3 Huffman 表、4 inflate 段狀態 `S`、5 詞法段狀態 `Λ`、6 計畫 `Π`、7 指紋挑戰值 `r`、8 欄位指紋 `C_g`。
- 這些承諾只在證明之間使用，查驗端不需要計算 Poseidon2（不揭露的值不會被重算）。欄位揭露仍用第 3.4.4 節的 SHA-256 承諾。
- 編碼（2026-10-26 依 Round 7 的提案定案，`native/circuits/IMPLEMENTATION.md` Round 7）：
  - Poseidon2 海綿：寬度 4、rate 3、加法吸收、IV 為 `欄位數 << 64`、最後不足的部分補零、輸出 `state[0]`，與 Noir beta.15 的 `Poseidon2::hash` 及 bb.js 2.1.9 的 `poseidon2Hash` 相同；前像為 `[tag, salt, 欄位數, 欄位...]`。
  - 位元組打包：每 31 bytes 依大端序成一個整數，最後不足 31 bytes 的一組直接以剩下的位元組為大端整數（左側補零），不在右側補零。
  - `C_z` 的欄位：`[實際長度, pack31(z 補零到 MAX_COMPRESSED)...]`；`C_p[i]` 的欄位：`[i, 實際長度, pack31(明文補零到 SEG_PLAIN)...]`。容量以外的位元組必須為 0。承諾含實際長度，避免尾端補零的碰撞。
  - Huffman 表：字面／長度碼長 288、碼 288、距離碼長 32、碼 32，共 640 個欄位。
  - 段狀態 `S` 的欄位順序：pos、output、tokens、blocks、phase、kind、final_block、table_commitment、pending_len、pending_dist、a、b、stored_end。
  - 不存在的歷史段承諾與第一段的 `S_in` 都是常數 0，不存在的歷史段位元組約束為 0。存在的歷史段長度都是 `SEG_PLAIN`，承諾內含它的絕對段索引。
  - 網域常數與電路名稱以 ASCII 大端序轉成 Field（例如 `"diw-zkpdf-v1"`）。
- `C_z` 的容量 `MAX_COMPRESSED` 必須在 SHA 段與所有 inflate 段相同，否則承諾無法對上（只影響完整性，不影響健全性）。內容視窗的 SHA 是一段完整證明（內容視窗最多 130 區塊），所以 `C_z` 涵蓋整個 `z`。

#### 3.12.2 段的種類與連接

```
P_sha（第 1.2 節的視窗壓縮，可分成多段）  公開 H_s、H_e，並輸出 C_z = commit(1, salt, z)
P_inf[0..k-1]                          輸入 C_z；S_in → S_out；輸出 C_p[i]；讀取前面最多 32 KB 的明文段承諾
P_lex[0..m-1]                          輸入 C_z、C_p[jK..jK+K-1]；Λ_in → Λ_out；最後一段輸出錨點序數、總數與 C_g（3.12.5）
P_claim                                輸入 C_z、C_g；輸出欄位的 SHA-256 承諾與述詞結果（3.12.6）
```

`z` 是內容視窗的壓縮資料（已與公開的 RC4 金鑰流 XOR）。

#### 3.12.3 inflate 段 `pdf_inflate_seg_v1`

- 每段私密輸入整個 `z`（最多 `MAX_COMPRESSED` bytes），在段內重算 `C_z` 後比對公開輸入，再以位元位置讀取。
- 明文以固定大小 `SEG_PLAIN` 切段，最後一段補零，實際長度在狀態中。一個長度距離記號可以跨段：記號在開始的段解碼，剩下的複製長度與距離放進狀態。
- 回頭複製最遠 32,768 bytes。段 i 私密輸入前面 `W = ceil(32768 / SEG_PLAIN)` 個明文段，在段內重算它們的承諾，並與公開輸入 `C_p[i-W..i-1]` 比對（不存在的段為固定的空承諾）。複製以不可變的「視窗 ‖ 本段明文提示」陣列讀取，遵守第 3.4.1 節 Round 6 的規則（私密索引只讀不再寫入的陣列，本段每個位元組以常數索引 `assert_eq` 綁定）。
- 段狀態 `S` 的內容：
  - 位元位置、已輸出長度、記號序號；
  - 區塊序號、區塊階段（標頭、區塊內、已結束）、區塊種類、是否為最後區塊；
  - 目前動態表的承諾；
  - 待完成的複製長度與距離；
  - Adler-32 的 a、b；
  - 未壓縮區塊的結束位元位置 `stored_end`（段在未壓縮區塊中間開始時需要它）。
- 未壓縮區塊沒有符號 256：區塊在 `stored_end` 結束，若 BFINAL 為 1 則串流結束。「最後區塊以 256 結束」只適用於 Huffman 區塊。
- Huffman 表：區塊在本段開始時，在段內由碼長重建，並計算表承諾放進狀態。本段從區塊中間開始時，私密輸入展開後的表，以承諾比對。每段最多 `SEG_BLOCK_STARTS` 個區塊開始。明文段大小固定，所以證明者不能改在區塊開始處切段；正式參數用 `SEG_BLOCK_STARTS = 1`，某一段含兩個以上區塊開始時，證明者在產生前拒絕並說明（樣本都是單一動態區塊，zlib 的區塊通常遠大於一段）。改成可變長度的段需要重新設計 `W` 的歷史上限，v1 不做。
- 公開輸入依序為：
  1. 網域常數與電路名稱；
  2. 段索引 i、是否第一段、是否最後一段；
  3. `C_z`、`S_in`、`S_out`、`C_p[i]`；
  4. `C_p[i-W..i-1]`。
- 第一段在段內檢查 zlib 標頭與初始狀態（不使用 `S_in`）。最後一段在段內檢查最後區塊以 256 結束、Adler-32 等於尾端 4 bytes、位元位置在資料範圍內。
- 查驗端檢查：段索引由 0 連續到 k-1；第一段的旗標、最後段的旗標正確；`S_out[i] = S_in[i+1]`；每段的 `C_z` 都等於 `P_sha` 輸出的 `C_z`；`C_p[i-W..i-1]` 等於前面各段輸出的 `C_p`。

#### 3.12.4 健全性要點

- 每段的狀態與明文都由承諾綁定；Poseidon2 的抗碰撞性讓證明者無法在兩段之間換狀態或換明文。
- 所有段都以同一個 `C_z` 讀取同一份壓縮資料，而 `C_z` 由 SHA 段在雜湊時一併計算，所以解壓的是被簽章涵蓋的位元組。
- 段可以由證明者任意切分，但狀態完整描述了 inflate 的進度，所以任何合法切分的串接都等於整個串流的 inflate。
- 段的切分固定為每 `SEG_PLAIN` bytes 一段，狀態完整描述了 inflate 的進度（含跨段的複製與未壓縮區塊的位置），所以段的串接等於整個串流的 inflate（Round 7 的論證）。
- 零知識：公開輸入只有加鹽承諾、段索引與首尾旗標；段數會透露明文長度的範圍（`SEG_PLAIN` 的倍數），描述檔要說明這點。
- 記號密度：每段最多 `SEG_TOKENS` 個記號。平均密度足夠不代表每一段都足夠，證明者（M3c 的見證產生）在產生前逐段檢查，不足時拒絕這組參數並說明，不自動改變切段。

#### 3.12.5 詞法段 `pdf_lex_seg_v1`

詞法段把第 3.4.2–3.4.4 節與第 3.5 節的檢查改為串流處理，**不再需要文字運算子表提示**（`MAX_OPS` 只是運算子數的上限）。

- 段 j 涵蓋 inflate 段 `jK .. jK+K-1` 的明文（`SEG_LEX = K × SEG_PLAIN` bytes），私密輸入這些明文段並重算 `C_p` 與公開輸入比對。超過最後一個 inflate 段的位置，`C_p` 為 0、明文為 0，而且之後不能再有段（本段必須是最後一段）。K 由量測決定。
- 逐位元組的狀態機與第 3.4.2 節相同：一般、註解、字面字串（巢狀括號深度、跳脫）、十六進位字串、字典（`<<`、`>>`）、名稱、數字、運算子記號。運算子記號只辨識需要的 `BT`、`ET`、`Tf`、`Tj`、`TJ`、`'`、`"`、`BI`、`BDC`、`BMC`、`Do`，其他一律視為「其他運算子」。
- Word 類規則（第 3.5 節）在段內直接檢查：
  1. 出現 `BI` 就不成立；字典內不得有字串（涵蓋 `BDC` 的屬性字典與 ActualText）。
  2. 陣列外的字串之後，下一個運算子必須是 `Tj`、`'`、`"`；陣列內的字串，陣列必須以 `]` 結束且下一個運算子是 `TJ`。字串只能出現在 BT…ET 內。
  3. 顯示文字的運算子之前，同一個 BT 內必須有 `Tf`（遇到 BT 清空目前字型）。`Tf` 的字型是它之前最近的名稱記號（最長 16 bytes，超過就不成立）。
  4. 同一個運算子中的字串種類必須相同（全為字面或全為十六進位），否則不成立。
- 每個顯示文字的運算子是一筆「文字運算子」，依串流順序編號 `0, 1, ...`（最多 `MAX_OPS`）。它的紀錄位元組與第 3.4.4 節相同：`u8 字型名稱長度 ‖ 字型名稱 ‖ u8 種類 ‖ u16 長度 ‖ 字串原始位元組`，原始位元組為所有字串去掉外框後的串接（不解跳脫、不解碼）。
- **指紋**：以挑戰值 `r` 計算位元組序列的多項式指紋 `fp(b_0..b_{n-1}) = Σ b_k · r^{n-1-k}`，逐位元組以 `fp ← fp·r + b` 更新，同時記錄 `r^n`。紀錄的指紋為 `fp(標頭) · r^{原始長度} + fp(原始位元組)`，所以標頭中的長度可以在運算子結束時才補上。
- **計畫 `Π`**（tag 6）：私密的錨點運算子編號（`MAX_ANCHORS` 個）與每個欄位的紀錄位元組提示（`MAX_CLAIMS × MAX_CLAIM_SRC`，含實際長度）。`Π` 在第一個詞法段計算，放進狀態一路傳遞，`P_claim` 以同一個 `Π` 開啟。
- **挑戰值** `r = Poseidon2([7, C_z, Π, A])`，`A` 是公開錨點資料的打包。`r` 在明文（由 `C_z` 決定）與欄位提示（在 `Π` 中）都固定之後才決定，所以 Schwartz–Zippel 成立：兩個不同序列的指紋相等的機率不超過長度除以欄位大小。**不可**讓證明者在知道 `r` 之後才選擇被比對的資料；若 `r` 只由公開資料決定，證明者可以用格約化找出指紋相同、內容不同的小係數序列。
- 錨點：公開輸入每個錨點的字型名稱、種類、原始位元組（第 3.6 節第 5 項）。每段由公開資料算出錨點紀錄的指紋。每個文字運算子結束時，與每個啟用的錨點比對指紋，相等時該錨點的計數加一；運算子編號等於該錨點在 `Π` 中的編號時，必須相等，並記下當時的計數作為序數。最後一段公開序數與總數。
- 欄位：欄位 slot 涵蓋前後兩個錨點之間（不含錨點）的文字運算子。v1 要求各啟用欄位的運算子範圍互不重疊，並依 slot 順序遞增（第一段在 `Π` 上檢查），所以同時只有一個欄位在累積：運算子結束時，若它在目前欄位的範圍內，以 `G ← G · r^{紀錄長度} + fp(紀錄)` 併入。欄位範圍結束時把 `(G, 長度)` 存入該 slot。最後一段輸出 `C_g = commit(8, salt, [各 slot 的 G 與長度])`。
- 段狀態 `Λ`（tag 5）包含：全域位置、狀態機模式、括號深度、跳脫狀態、字典深度、陣列旗標、BT 旗標、目前字型（16 bytes ＋長度）、最近名稱（16 bytes ＋長度）、運算子記號緩衝（最多 3 bytes ＋是否過長）、待顯示字串旗標與種類、目前運算子的指紋與長度、運算子編號、各錨點的計數與序數、目前欄位的 G 與長度、各欄位的結果、`Π`、`r`。第一段的 `Λ_in` 為 0（初始狀態）。
- 最後一段：狀態機必須在一般模式、沒有待顯示的字串、不在 BT 內，各啟用錨點都已找到（序數不為 0）。
- 公開輸入依序為：網域常數與電路名稱；段索引 j、是否第一段、是否最後一段；`C_z`、`Λ_in`、`Λ_out`；`C_p[jK..jK+K-1]`；錨點資料（第 3.6 節第 5 項，序數與總數只在最後一段有意義）、欄位 slot 的啟用旗標與前後錨點索引；最後一段的 `C_g`。
- 查驗端檢查：段索引連續；`Λ_out[j] = Λ_in[j+1]`；`C_p` 依序涵蓋全部 inflate 段，最後一個 inflate 段落在最後一個詞法段；各段的 `C_z` 與錨點資料相同。

#### 3.12.6 欄位段 `pdf_claim_v1`

- 私密輸入 `Π` 的開啟資料（錨點編號與欄位紀錄提示）與 `salt`；公開輸入 `C_z`、錨點資料、`C_g`。段內重算 `Π`、`r`，以 `r` 算出每個欄位提示的指紋並組成 `C_g`，必須等於詞法段的輸出。這證明欄位提示就是兩個錨點之間的紀錄。
- 由欄位提示計算第 3.4.4 節的 SHA-256 承諾（公開，第 3.6 節第 6 項），並以第 3.4.5 節的方式檢查述詞（數字對照表、述詞為公開輸入）。β 也是這一段的公開輸入。
- SHA-256 的成本隨欄位數增加；若超過段的大小，`P_claim` 可以依欄位 slot 分成多段，每段都重算同一個 `Π` 與 `C_g`。

#### 3.12.7 段參數（Round 7 量測，2 vCPU）

| 等級 | inflate 段 `SEG_PLAIN / SEG_TOKENS / SEG_BLOCK_STARTS / MAX_COMPRESSED / W` | gates（dyadic） | 每段 warm prove |

| A 手機 | 2048 / 288 / 1 / 8192 / 16 | 974,643（2^20） | 44 秒 |
| 電腦 | 4096 / 576 / 1 / 8192 / 8 | 1,275,375（2^21） | 66 秒 |

## 4. C2：zkTLS（TLSNotary）

### 4.1 版本與模式

- tlsn `v0.1.0-alpha.15`（以 commit 釘選）。Proxy 模式為預設：查驗方自己連到目標網站並轉送加密封包，證明者在 ZK 中證明 TLS 1.2 PRF、Finished 與記錄的正確性【確認：TLSNotary Proxy mode 文章】。MPC 模式為選項，查驗方想避免「查驗方到網站之間的網路被劫持」的假設時使用，代價是頻寬與時間。
- 只支援 TLS 1.2；描述檔記錄目標網站的 TLS 版本與加密套件（學信網、移民署查驗頁都支援 TLS 1.2 ECDHE-RSA-AES128-GCM-SHA256【確認：2026-10-11 openssl 測試】）。
- 請求一律帶 `Accept-Encoding: identity` 與 `Connection: close`，避免壓縮的回應無法部分揭露。chunked 回應的規則對的是去掉分塊標頭後的內容，欄位跨越分塊時揭露範圍包含中間的分塊標頭（CRLF、分塊大小列），查驗方讀取前去掉；持有端只揭露查驗方能以同一規則讀回同一片段的範圍（`ChunkedBody`）。
- 上限：送出 4 KB、接收 256 KB（描述檔可降低）。學信網新版中文報告（桌面版面）實測約 32 KB，未含照片圖檔。

### 4.2 查驗頁描述檔

```json
{
  "id": "cn.chsi.xjbg/1",
  "title": "學信網學籍在線驗證報告",
  "host": "www.chsi.com.cn",
  "official": false,
  "prepare": { "type": "none" },
  "request": {
    "method": "GET",
    "path": "/xlcx/bg.do",
    "query": "vcode={vcode}&srcid=bgcx",
    "headers": { "User-Agent": "Mozilla/5.0" },
    "inputs": [ { "name": "vcode", "label": "在線驗證碼", "pattern": "^[0-9A-Z]{12,16}$", "private": true } ]
  },
  "limits": { "maxSent": 1024, "maxRecv": 65536 },
  "status": { "reveal": "<title>[^<]{1,80}</title>", "success": "^<title>教育部学籍在线验证报告_…</title>$" },
  "fields": [ { "name": "name", "label": "姓名", "reveal": "<div class=\"label\">\\s*姓名\\s*</div>\\s*<div class=\"value[^\"]*\">([^<]{1,40})</div>" } ]

```

完整描述檔在 `templates/zktls/cn.chsi.xjbg.json`（2026-10-24 以真實報告核對）。學信網沒有 User-Agent 會回 403，且依 User-Agent 回傳桌面或手機版面，所以描述檔固定 `Mozilla/5.0`；`Accept-Encoding` 與 `Connection` 由規劃器加上。

- `prepare.type` 可為 `none` 或 `captcha`（`ZkTlsPrepare`）：持有端在 zkTLS 之外以一般 HTTPS 開 `page` 取得工作階段，在同一工作階段取得 `image` 的驗證碼圖片給使用者看，使用者輸入到 `input`；`cookies` 列出的工作階段 Cookie 放進查詢請求的 Cookie 標頭，與輸入一樣不揭露。每次查詢用掉一張圖，重試或取消時在同一工作階段換新。移民署查驗頁屬於後者（`templates/zktls/tw.gov.immigration.entryexit.json`，送出證號、序號與驗證碼；表單原為 multipart，實測接受一般表單編碼；2026-10-24 以真實證明書核對：結果頁的列表只有日期、證號與序號，資料在隱藏的明細區塊，出入境列表新到舊排列，第 1 列為最近一次出境與其後的入境）。戶政司電子戶籍謄本驗證頁（2026-10-24 以真實檢查號核對，不實作）表單帶每次不同的 `_csrf` 與 `captchaKey`，以 `prepare.values` 從表單頁讀出；驗證碼圖片網址含 `captchaKey`；以 multipart 送出（含空的 `uploadFile` 檔案欄位）。驗證碼錯誤時回到表單並換新的 `captchaKey`；成功頁只有「檢查號經驗證無誤」、驗證時間與帶回的檢查號，謄本明文需自然人憑證或行動自然人憑證登入下載，zkTLS 無法揭露謄本內容，只能證明「某張謄本有效」，使用者決定不做這個查驗頁（取代方式：文件本身的簽章與衍生憑證）。查到的表單機制（`prepare.values`、multipart、輸入的 `document` 規則）保留為通用功能。檢查號開頭 8 碼為產製日期，中段推測含申請人身分證字號（格式相符，未經官方說明確認），應視為個資，只作為不揭露的輸入；網站的 TLS 1.2 加密套件尚未在雲端環境以外確認（雲端出口經代理）。
- `reveal` 是對回應主體的規則：以描述檔的正規表示式找出「標籤加值」的完整片段，揭露整個片段，查驗方再用同一個正規表示式取出值。揭露片段的位置與長度公開。
- `official` 只表示網站屬於政府，不改變信任等級（p4-zkp.md 第 6 節）。
- 描述檔不得含任何真實查詢結果；查詢輸入所在的列（例如報告上的在線驗證碼）不可作為欄位。

### 4.3 證明者在請求中隱藏的內容

整個請求只揭露請求行的方法與路徑（不含查詢字串）與 `Host`。查詢字串、表單、cookie、`Content-Length` 都隱藏。

### 4.4 結果

查驗方得到：伺服器名稱與憑證鏈、連線時間、揭露的回應片段、解析出的欄位與狀態。即時模式不產生可攜帶的證明；要存證時改用自架 notary 簽發網頁證明憑證（p4-zkp.md 第 5.2 節）。

### 4.5 C2b：隱藏值述詞（後續）

GovBind 的做法：證明者對回應的某個範圍做 SHA-256 承諾（tlsn 支援 `HASH` 承諾與開啟），查驗方得到承諾值；另一個 Noir 電路以私密的範圍內容重算承諾並證明述詞（例如日期早於某日、狀態為有效）。介面保留：`ZkTlsCommitment(range, alg = SHA256, digest)`；電路 `tls_predicate_v1` 在第二版設計。

- Android：以 Bonds 的 `predicate.rs` 與 `zkid-mobile.patch` 為基礎，改用 cargo-ndk 輸出 `arm64-v8a`、`x86_64`；證明執行緒需 64 MB 堆疊。持有端另需下載 `jwt_2k` 與 `show` 的見證計算圖（安裝後約 94 MB）。公開訊號由我們自己的 uniffi 匯出，可避開 Bonds 在 iOS 上無法取得公開訊號的限制。
- Bonds 已知限制沿用並在畫面寫明：自發卡的發行端 DID 是穩定假名；憑證效期不在電路內；公路局駕照電子卡沒有生日欄位，不能做。
- 查驗結果的語意（2026-10-22 審查 PR #17 決定）：`verify_age_presentation` 為 true 只表示「指定發行端公鑰簽過的憑證，其出生日期不晚於 cutoff，且綁定這次的 nonce 與裝置金鑰」。Prepare 與 Show 的公開值沒有憑證效期與查驗時間，持有端只在建立 Prepare 輸入時以本機時間檢查 `exp`、`nbf`，查驗端無法得知憑證目前是否有效或已撤銷，結果型別與查驗畫面都不得宣稱已驗證效期或狀態。要證明目前有效需新版電路，不在 openac-age-v1 範圍。
- 憑證容器（同日決定）：openac-age-v1 只支援 Bonds／TWDIW 的 `vc.credentialSubject._sd` 容器（`typ` 可為 `vc+sd-jwt`、`dc+sd-jwt` 或 `JWT`）。根層 `_sd` 的標準 IETF SD-JWT VC 一律以固定錯誤拒絕，Kotlin 端不對這類憑證提供 OpenAC 選項；標準 mdoc 的年齡證明走 C4 Longfellow。
- 原生匯出（同日整合）：OpenAC 的 UniFFI 函式在每個建置都存在（綁定載入時會核對每個函式的 checksum），`-Pdiw.zkFeatures=openac`（或 `DIW_ZK_FEATURES`）才連結後端，未連結時一律回 `Unsupported`。建置 OpenAC 需要 protoc 與 libclang。

## 6. C4：Longfellow（mdoc）

- 由 Multipaz `LongfellowZkSystem` 提供，電路檔內建（v6、v7，1–4 個屬性）【確認：zkp-verifier.md 1.2】。
- 持有端：`ResponseBuilder` 的 `mso_mdoc_zk` 路徑已存在，註冊 `ZkSystemRepository` 後即可用；ISO 18013-5 近距離要在 `ProximityModel` 處理 `ZkRequest`；DC API 的 `org-iso-mdoc` 同樣支援。
- 查驗端：`PresentationVerifier` 傳入同一個 repository；查驗方必須事先有發行端的 IACA 或 DS 公鑰（ZK 證明隱藏了 MSO）。
- 發行端限制：MSO 不得超過 2,533 bytes，測試發行端要產生 ZK 友善的 mdoc【確認：P0 驗證】。
- 實作（WP8，2026-10-17）：`core/zk/LongfellowZk` 只接受內建電路且參數完全相同的 spec，產生後先自驗；查驗時拒絕帶 deviceSigned 的證明，證明時間與現在相差不得超過 5 分鐘。明確要求 ZK（`zkRequired`）的近距離請求，在同意前確認有相容電路，不退回一般 mdoc。原生函式庫只有 Android arm64-v8a、x86_64 與桌面 Linux x86_64、macOS arm64；其他平台（含 Windows）`repository` 為 null 並提供不支援原因。

## 7. 安全審查重點（給 Review）

- 第 1.2 節的中間狀態銜接是 zkPDF 唯一的完整性來源，Review 時以 Z2、Z3 測試與程式碼逐行確認：查驗端自己計算 H_s，不採用套件附帶的值。
- 第 3.4.2 節的完整性指標：漏掉一個字串時證明必須不成立（Z13）。
- 第 3.3 節 V5：只用簽章涵蓋版本的 xref；不得用之後增量更新的 xref 去找內容串流。
- 零知識設定（第 1.1 節規則 2）。
- OpenAC：查驗端的期望值全部由查驗方輸入產生；證明產生後一律自驗。
- zkTLS：請求中的私密內容不可出現在揭露範圍或錯誤訊息；描述檔的正規表示式只在揭露片段上執行。
- zkTLS 通道：Noise 的 prologue 必須是請求 JWS 的 SHA-256，回應方公鑰必須是請求內的 `ck`；區域網路路徑只接受私有位址；中繼不得因配對失敗而改用其他路徑傳送明文。
- 第 3.11 節：查驗端的正規化只作用在揭露的欄位文字上，且依描述檔版本選擇；錨點標籤比對不得使用部分比對。
