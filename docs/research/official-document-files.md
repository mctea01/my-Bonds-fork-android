## 個人錢包與機關交換權限（2026-10-16）

本專案可匯入、解析、健檢、驗證及封裝電子公文函 XML／SI／DI、簽署並保存 CAdES／XAdES、時戳與撤銷證據。正式電子公文交換中心的機關註冊、交換帳號及機關專用憑證不屬一般個人錢包可取得的資格；**只完成公開格式的實作正是目前的預期交付**，不以可直接向政府交換平台收發文作為驗收標準。不得用模擬 REST 路徑冒充機關正式交換 API。

## 名詞

| 名詞 | 說明 | 錢包中的對應 |
|---|---|---|
| 文書本文檔（DI，Document Instance） | 文書本文的 XML，依文書處理手冊的 DTD（104 系列）組成，例如「函」 | `.di`，公文容器的主體；`OfficialDocuments` 以結構化畫面呈現 |
| 簽核電子檔（SI，Sign Instance） | 線上簽核的文字化紀錄，記錄各簽核點的簽核結果與過程、外部檔案連結與驗證資訊，是主要的作業與憑據檔案 | `.si`，根元素「線上簽核」；`ApprovalSignatures` 驗證每個簽核點，`OfficialBundles.approvalPoints` 讀出各簽核點涵蓋的檔案 |
| 外部檔案 | SI 以外、由 SI 參照的檔案：來文、本文、附件檔、文稿頁面檔 | 公文容器的成員（`StoredFile.bundleOf`） |
| 附件檔 | 文字檔、圖片檔、工程圖檔、聲音檔、文字影像檔等 | 一般檔案，依格式檢查與預覽 |
| 文稿頁面檔 | 線上簽核的視覺化紀錄：以影像記錄各簽核點人員完成作業後、清稿前的稿面，輔助重現原文原意 | TIFF 等影像，`TiffDecoder` 預覽 |
| 詮釋資料（metadata） | 描述檔案背景、內容、關聯與資料控制的資訊 | 錢包不產生；封裝檔內的詮釋資料尚未解析 |
| 封裝檔 | 把電子檔案、詮釋資料與驗證真實性、完整性的資訊以包裹方式儲存 | 錢包的「匯出公文容器」是一般 ZIP，不是封裝檔格式 |

| 交換表單檔（SW）、文書訊息檔（DM）、信封檔（EN）、加密交換表單檔（ESW）、跨機關陳核會稿交換表單檔（CO） | 公文電子交換用的表單：收文機關、訊息代碼、會陳狀態。交換時由公文交換系統以機關憑證加解簽章與加密，表單本身不含簽章 | 公文容器的成員；檢查結果「沒有簽章」是正常的，不代表檔案有問題 |

電子檔案的架構：簽核電子檔參照外部檔案（文書本文檔、附件檔、文稿頁面檔），外層再由檔案管理單位加上詮釋資料與點收簽章。

## 線上簽核的規則

### 誰要簽、用什麼簽

- 各簽核點人員與繕校人員，不論是否修改文稿，都要以電子憑證簽章；收文與登記桌人員可以不簽（第十點第十款）。
- 憑證須符合電子簽章法，並依「行政院及所屬各級公務人員電子識別證管理作業要點」選用經濟部核定的憑證機構簽發的憑證，例如自然人憑證、公務人員電子識別證。
- 本人憑證無法使用時，可用機關核發的臨時憑證（SI 記為「借卡」，含借卡日期與原因），歸檔前要以本人憑證補簽（「補簽追認」，記錄補簽的簽核點、補簽註記如本人補簽或離職代簽）；無法補簽時由職務代理人或權責主管補簽並記錄原因（第十點第四款）。
- 簽章採 XML Signature：正規化 Canonical XML 1.0、摘要 SHA256、簽章 RSA-SHA256，KeyInfo 放 X509 憑證（附錄 3 表 3-5）。
- 歸檔點收時，檔案管理人員確認簽核電子檔的資訊無誤後，附加機關憑證電子簽章，再產生封裝檔（第十八點）。

### 流程（附錄 2 圖 2-3）

1. 承辦人員擬辦，設定簽會流程（`線上簽核流程` 的 `簽核流程` 節點，可有分會點與不需加簽的流程點，例如登記桌）。各簽核點可再調整流程。
2. 每個簽核點：先檢查前一個簽核點的真實性與完整性，再編輯文稿、附件或簽核意見，最後附加憑證、寫入簽核電子檔，傳送下一流程。
3. 修改附件時，檔名要附加版本資訊（第十點第九款）；跨機關會簽的修改另加機關代碼。
4. 核定（決行）後發文或結束；有臨時憑證簽核的簽核點，歸檔前補簽追認。
5. 線上與紙本可以互轉，紙本轉線上要退回原承辦人重辦（第十點第八款）。

### 簽核電子檔（SI）的結構

副檔名 `.si`，各簽核點逐層累加；`SignedInfo` 要記錄前次簽核點、本次簽核點與外部檔案的雜湊值（第十點第十二款）。依 `104_sign_utf8.dtd`：

```
線上簽核 (Id)
  線上簽核流程 (Id)
    簽核流程 (Id, 異動別)：分會點（內含簽核流程）或流程點（流程別），可重複
  線上簽核資訊 (Id)
    簽核點定義 (Id, URI 指向簽核流程的 Id)，一個以上
      Signature：SignedInfo、SignatureValue、KeyInfo
      Object (Id)
        異動資訊 (退文 Y/N, 借卡 Y/N)
          簽核人員：機關?、單位、職稱、姓名、帳號、角色?
          異動別、簽核意見*（可用 URI 指向文稿）、簽章時間（民國年 3 碼、月日時分各 2 碼）
          次位簽核人員*、借卡?（借卡日期、借卡原因）
        簽核資訊
          來文文件夾（最初簽核點）或來文文件夾參照路徑（之後的簽核點），可省略
          簽核文件夾：簽核文稿清單（文稿：名稱、文稿類型、文稿頁面檔?、附件清單?）、
                      檔案清單（電子檔案資訊：檔案名稱、檔案大小、檔案格式）、併文清單?
          或子文簽核文件夾（併辦的子文）
    補簽追認?：補簽人員 (URI 指向簽核點, 補簽註記, 產生時間)，內含簽章資料（簽核人員、Signature）
```

文稿、附件與電子檔案資訊都以「原始檔序號」對應檔案清單中的實體檔案；附件分電子檔格式附件（XML、PDF 等）、一般頁面檔格式附件（TIFF 等頁面影像）與文稿頁面檔格式附件。

異動別是最多 10 字的自由文字。規範的範例：簽核流程的異動別為「擬辦、陳核、核定」，異動資訊的異動別為「分文、送會」；其他常用的有會辦、核稿、決行、代決、繕校。

### 錢包的對應

| 規則 | 錢包 |
|---|---|
| 驗證每個簽核點 | 依檔名比對外部檔案的 SHA-256、簽章值、憑證鏈與信任等級，並檢查是否涵蓋自己的異動資訊與前一個簽核點 |
| RSA-SHA256、Canonical XML 1.0 | 加簽一律用 Canonical XML 1.0；RSA 憑證用 RSA-SHA256。驗證時其他演算法照常檢查，但註明不符規範 |
| 經核定憑證機構的憑證 | 自然人憑證卡、行動自然人憑證、PKCS#12、CSC 皆可；錢包金鑰是自簽 ECDSA，簽署畫面警告機關系統不會接受 |
| 借卡與補簽追認 | 驗證時列出借卡的簽核點是否已有補簽追認，補簽追認本身的簽章成立才算；錢包不產生借卡與補簽追認 |
| 簽核人員與文稿清單的必要欄位 | 加簽時寫入單位、職稱、帳號（未填寫為空白）與簽核文稿清單：.di 為文稿，其他檔案（交換表單除外）為第一份文稿的附件，TIFF 為頁面檔格式附件 |
| 文稿頁面檔、次位簽核人員、來文文件夾 | 不產生；錢包不是公文系統，不能擬稿、清稿、發文、交換或歸檔點收 |

錢包加的簽核點用於個人保存與驗證；機關的公文系統是否接受，取決於該系統的流程設定與憑證註冊（自然人憑證通常要先在公文系統註冊）。

## SI 的簽核點

錢包讀到的公開範例與規範的 DTD（104_sign）一致：每個「簽核點定義」內是一個不帶命名空間的 XMLDSig `Signature`，SignedInfo 參照：

1. 以檔名指向的外部檔案（分離式，原始位元組的 SHA-256，摘要方法可能寫成 `xmldsig-more#sha256`）；
2. 前一個簽核點；
3. 自己的 `Object`（異動資訊：簽核人員、異動別、簽核意見、民國年月日時分的簽章時間；簽核資訊：文稿清單與檔案清單）。

因此每個簽核點都固定了「這個時間點」各外部檔案的內容。同一個檔名在不同簽核點可以有不同摘要（文稿在簽核過程中被修改），文稿頁面檔用來保留每個簽核點當時的稿面。

錢包的兩層容器依這個結構排列：每個檔案列在第一個以相同摘要簽署它的簽核點下；同名但摘要不同時，該簽核點標示「內容與這個簽核點簽署時不同」，常見原因是容器內只保存了之後修改的版本。

## 與國際標準的對照

規範的文字寫「採用 XML Signature 規範」，演算法也是標準的：Canonical XML 1.0（`http://www.w3.org/TR/2001/REC-xml-c14n-20010315`）、SHA-256、RSA-SHA256（RFC 4051 `xmldsig-more#rsa-sha256`），以 X.509 憑證表明簽署者。但 SI 的寫法是規範自己的 XML 方言，不是 W3C XML Signature（XMLDSig）或 ETSI XAdES 的文件，一般的簽章程式庫不能直接驗證。逐項如下：

| 項目 | 國際標準 | 電子公文規範（104_sign） | 影響 |
|---|---|---|---|
| 命名空間 | XMLDSig 的元素必須在 `http://www.w3.org/2000/09/xmldsig#` 命名空間 | DTD 沒有宣告 `xmlns`，Signature 與子元素不帶命名空間；加上命名空間反而不符 DTD | Apache Santuario、.NET SignedXml、JDK `javax.xml.crypto` 找不到 Signature；補上命名空間會改變正規化結果，簽章值就不成立。只能由認得這個方言的程式驗證 |
| SignatureValue | 必要 | DTD 寫成可省略（`SignatureValue?`） | 結構上允許沒有簽章值的簽核點（教材案例 5「使用線上簽核但沒有以憑證加簽」）；錢包不把沒有簽章值的簽核點算成已簽章 |
| KeyInfo | 可放多種金鑰資訊、憑證鏈 | 只能一個 `X509Data`，內含一張 `X509Certificate` | 只有簽署者憑證，中繼憑證要由驗證端補（錢包以 AIA 與內建 GPKI 中繼憑證補鏈） |
| 外部檔案的參照 | URI 可以是任何 URI，相對 URI 的解析由應用程式決定 | 以檔名當 URI，分離式，對原始位元組取摘要，沒有 Transform | 符合 XMLDSig 的分離簽章，但檔案必須與 SI 放在一起並保持原檔名；改名或用其他方式打包就無法比對（錢包匯出公文容器時把檔案以原檔名放在 ZIP 最上層） |
| 同文件參照 | `#Id` 需要 ID 型別的屬性 | 屬性 `Id` 由 DTD 宣告為 ID；Object 是 Signature 的兄弟節點，前一個簽核點以 `#Id` 串接 | 符合 XMLDSig；但不讀 DTD 的程式不知道 `Id` 是 ID，要自行登記（錢包的驗證不依賴 DTD） |
| 摘要演算法 URI | SHA-256 的標準 URI 是 `http://www.w3.org/2001/04/xmlenc#sha256`；RFC 4051 的 `xmldsig-more#` 只定義 sha224、sha384 | 規範只寫「SHA256」，沒有指定 URI；公開範例寫 `xmldsig-more#sha256` | 範例的 URI 不在任何標準內。錢包驗證時兩者都接受；加簽沿用範例的寫法，以便機關系統比對 |
| 簽署時間 | XAdES 的 `SigningTime` 是 xsd:dateTime（含時區），另可加 RFC 3161 簽章時戳 | 「簽章時間」是民國年 3 碼加月日時分，沒有秒與時區，放在被簽的 Object 內 | 時間有被簽章保護，但只是簽署者自己宣稱的時間；沒有第三方時戳，無法證明簽署當時憑證有效 |
| 簽署憑證綁定 | XAdES 以 `SigningCertificateV2` 把憑證摘要放進簽章範圍 | KeyInfo 不在 Reference 內，憑證沒有被簽 | 理論上可以換成同一把公鑰的另一張憑證；實務上自然人憑證每張金鑰不同，風險低 |
| 長期驗證 | XAdES B-T、B-LT、B-LTA 加時戳、憑證與 OCSP／CRL、封存時戳 | 簽核點不帶時戳與撤銷資訊；改由歸檔點收時加機關憑證簽章並產生封裝檔（第十八點） | 未歸檔前的 SI，在簽署憑證過期或廢止後就無法單獨證明簽署當時有效。錢包可另外取得 RFC 3161 時戳並保存每個簽核點憑證鏈的 OCSP 與 CRL，補上這一塊 |
| 演算法彈性 | XMLDSig 1.1 支援 ECDSA、RSA-PSS 等 | 只用 RSA-SHA256 | 與自然人憑證（RSA 2048）相符；錢包金鑰（ECDSA）加的簽核點會註明不符規範 |
| 編碼 | XML 1.0 任何編碼 | 104 系列使用 UTF-8 | 錢包加簽只接受 UTF-8 的 SI |

結論：密碼學的選擇（C14N 1.0、SHA-256、RSA-SHA256、X.509）是標準且目前仍安全的；結構上是 XMLDSig 的子集加上去掉命名空間的變形，互通只限國內公文系統與檔案管理局的工具，不是 XAdES，也沒有長期驗證資料。錢包依規範產生 SI（以 xmllint 對附錄 5 之三的 DTD 驗證錢包產生的簽核檔，沒有錯誤），驗證時列出不符規範的地方（演算法、正規化、缺少流程參照、借卡未補簽），並以時戳與撤銷資訊補足長期驗證。

## 健檢類別

檔案管理局的「電子封裝檔工具箱」（電子檔案檢測與瀏覽、技術鑑定、移轉）檢測封裝檔的五類項目，錢包對應如下：

| 工具箱檢測 | 內容 | 錢包 |
|---|---|---|
| 格式檢測 | 封裝檔與 XML 是否符合 DTD | 解析 XML（不載入外部 DTD），App 內不做 DTD 驗證；錢包產生的 SI 在開發時以 xmllint 對規範的 DTD 驗證 |
| 資料檢測 | 欄位值是否符合規範（例如文別序號） | 未實作 |
| 外部檔案檢測 | 外部檔案是否遺失、格式與雜湊值 | 容器健檢：檔案齊全或缺少、與簽核時不同（依 SI 的摘要） |
| 憑證檢測 | 簽核憑證與憑證鏈 | 每個簽核點的憑證鏈與信任等級（GPKI 等內建錨點），可保存 OCSP 與 CRL |
| 簽章檢測 | 簽章值與雜湊值 | 每個簽核點的簽章判定；外部檔案遺失時簽章檢查也會不完整（工具箱與錢包相同） |

技術鑑定報告另統計檔案格式、保存年限、版本、憑證與雜湊演算法強度；錢包只對單一案件呈現，不做統計。

## 教材列出的常見問題

| 案例 | 問題 | 錢包的處理 |
|---|---|---|
| 1 | XML 宣告的編碼與實際存檔編碼不同，造成中文轉碼問題 | 加簽核點只接受 UTF-8 的 .si，其他編碼拒絕並說明；讀取時依 XML 宣告解析 |
| 2 | 自訂表單沒有提供 DTD，格式檢測失敗 | 不做 DTD 驗證，不受影響 |
| 3 | 文別序號定義不符規範 | 不檢查 |
| 4 | 系統在案卷著錄時才寫入詮釋資料，報告沒有檔號與文號 | 不適用 |
| 5 | 使用線上簽核但沒有以憑證加簽 | 簽核點沒有 Signature 時不列為已簽章，健檢顯示簽核點數與簽章結果 |
| 6 | 舊規範（94 年）的「簽章時戳」欄位在 99 年後已改名 | 錢包只讀「簽章時間」，舊欄位不影響簽章驗證 |

## 長期保存格式

教材建議長期保存的 PDF 符合 PDF/A（ISO 19005，PDF/A-1b 為最低要求）：不含音訊視訊、不可執行 JavaScript 或夾帶附件、文字內嵌、色彩與設備無關、避免透明物件、不可加密、必須含詮釋資料；可用 veraPDF 驗證。錢包目前不檢查 PDF/A 符合性；錢包製作的 PDF（`PdfComposer`）使用閱讀器內建的 CJK 字型、沒有嵌入字型，不符合 PDF/A。
